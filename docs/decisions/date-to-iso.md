# How safeDateToIsoString writes a date

`safeDateToIsoString` is `Date.prototype.toISOString` that can't throw: the native text for any valid time, and the caller's fallback for anything else; [`safeParseDate`](safe-parse-date.md) reads one back.

## Decision

- **Signature:**

  ```ts
  safeDateToIsoString(value: unknown, options?: { fallback?: F }): string | F
  ```

- **The name** follows [When a name starts with `safe`](safe-prefix-naming.md): `safe` + the native method's path, `Date.prototype.toISOString`, with `Iso` cased like `Url` and `Uri`.
- **Accepted input:**
  - a `Date`, identified by brand check (`Date.prototype.getTime`), so one from another realm counts and an object that only looks like a date doesn't;
  - a finite number, read as milliseconds since the epoch exactly as `new Date(value)` reads it, a fraction truncated (`1700000000123.9` → `"2023-11-14T22:13:20.123Z"`) and `-0` the epoch;
  - a boxed number, unwrapped by brand check first.
- **Everything else returns the fallback:**
  - an invalid `Date` (`new Date(NaN)`), and a number outside the `Date` range of ±8.64 × 10¹⁵ ms (`8640000000000001`), where `toISOString` throws `RangeError`;
  - `NaN` and `±Infinity`;
  - strings, even ISO ones (`"2024-01-01"`): reading text into a date is parsing, which [`safeParseDate`](safe-parse-date.md) does, so `safeDateToIsoString(safeParseDate(text))` is the round trip;
  - booleans, `null`, bigints, and objects, which `new Date` coerces (`new Date(true)` is one millisecond past the epoch, and `new Date(null)` is the epoch itself).
- **The output is always `toISOString`'s exactly:** UTC, `Z`, and three fractional digits (`"1970-01-01T00:00:00.000Z"`).
  - Years 0000 through 9999 are four digits; any other year takes ECMAScript's expanded six-digit form with a sign, as the native method writes it: `"+010000-01-01T00:00:00.000Z"`, `"-000001-01-01T00:00:00.000Z"`, up to `"+275760-09-13T00:00:00.000Z"`.
  - `Date.parse` reads the expanded form back, so every result round-trips; a consumer that only takes four-digit years (strict RFC 3339) checks the range itself.

## Why

- `toISOString` throws `RangeError` on an invalid date, which any failed `new Date(text)` produces, so a timestamp written to a log or an API response needs a guard.
- The expanded year form is the native one, and the JavaScript tools agree on it: luxon and Day.js write `"+010000-…"` and `"-000001-…"` exactly as `toISOString` does.
  - The tools outside JavaScript split: date-fns writes `"10000-…"` with no sign, Go writes `"10000-…"` and `"-0001-…"`, Java writes `"+10000-…"`, and Python and .NET throw outside years 1 through 9999.
  - No two of those agree with each other, so matching the native form is the only choice that's predictable, and rejecting these years would lose dates JavaScript itself handles.
- Numbers are accepted because epoch milliseconds are how dates travel in JSON and databases (`Date.now()`, `getTime()`), and `new Date(number)` reads them the same on every engine; strings aren't, because `new Date(string)` doesn't.
- The other languages show what a guard buys: Java's `(long)` cast turns `NaN` into the epoch and `Infinity` into year 292278994, and Python's float arithmetic writes `253402300799999` as `"…59.998"`.
- GitHub code search, on 2026-10-21, found `safeDateToIsoString` in about 620 TypeScript and JavaScript files and `safeToISOString` in about 390; `toIsoDate` (about 79,000) and `dateToIso` (about 23,000) are commoner but name no native method, and `toIsoString` can't be counted apart from the native `toISOString`, since code search ignores case.

## Consequences

- A caller who wants local time, an offset, or another output format reaches for `Intl.DateTimeFormat` or a date library; `safeDateToIsoString` writes one format, the native one.
