# How upperFirst and lowerFirst change the first letter

`upperFirst(value)` uppercases a string's first character and `lowerFirst(value)` lowercases it, leaving the rest as it was; each returns the matching `Capitalize<S>` or `Uncapitalize<S>` type.

## Decision

- **The first code point is mapped, not the first UTF-16 unit,** so an astral letter changes too: `upperFirst("𐐨a")` is `"𐐀a"`.
- **Mapping is locale-free `toUpperCase` / `toLowerCase` by default,** so the result doesn't depend on the engine's ICU data or the user's locale.
  - Full case mapping applies, so the result can be longer: `upperFirst("ßa")` is `"SSa"`, and `upperFirst("ﬀa")` is `"FFa"`.
  - Uppercase, not titlecase: `upperFirst("ǆa")` is `"Ǆa"`, not `"ǅa"`, and a Georgian Mkhedruli letter becomes its Mtavruli capital (`"აბ"` → `"Აბ"`), since JavaScript has no titlecase mapping.
  - `lowerFirst("İA")` is `"i̇A"`, `toLowerCase`'s locale-free `i` plus a combining dot, not the Turkish `"iA"`.
- **Only the first code point changes:**
  - the rest keeps its case by default, so `upperFirst("hELLO")` is `"HELLO"`, unlike `capitalize` in lodash, es-toolkit, and Python, which lowercase it;
  - a leading non-letter is left alone, and nothing skips ahead to the first letter: `"'hello"`, `" hello"`, and `"123abc"` come back unchanged.
- **`upperFirst`'s `lowerRest: true` lowercases the rest,** `capitalize`'s behavior, in the same locale as the first letter: `upperFirst("hELLO", { lowerRest: true })` is `"Hello"`, typed `Capitalize<Lowercase<S>>`.
  - lodash's and es-toolkit's `capitalize` give the same answers, `"ßTRASSE"` → `"SStrasse"` included.
  - `lowerFirst` gets no `upperRest`; nothing measured offers it.
- **`locale` maps the first letter, and with `lowerRest` the rest, through `toLocaleUpperCase` / `toLocaleLowerCase`** (owner, 2026-10-28): `upperFirst("istanbul", { locale: "tr" })` is `"İstanbul"`, and `lowerFirst("Istanbul", { locale: "tr" })` is `"ıstanbul"`.
  - It takes one BCP 47 tag as a `string`, case-insensitive (`"TR"`); not a list, since `toLocaleUpperCase` uses only a list's first tag (`["xx", "tr"]` maps as `"xx"`), with no fallback search (owner, 2026-10-29).
  - A tag the engine rejects (`"not a locale!"`, which throws a `RangeError` natively) falls back to the locale-free mapping, so the call never throws.
  - With `locale` set, the return type widens to `string`: TypeScript's `Capitalize` is locale-free, so it would claim `"Istanbul"`.
  - **The result depends on the engine's locale data.** The Hermes CLI measured has no `Intl` and ignores the locale (`"Istanbul"` for Turkish), and .NET lacks Lithuanian's dotted `i̇̀`; without `locale` the function stays environment-independent.
- **The types are TypeScript's own `Capitalize<S>` and `Uncapitalize<S>`,** which make the same three choices: code point, full mapping, uppercase.
  - TypeScript 6.0 and later split on the code point too; 4.9 through 5.9 split on the first UTF-16 unit, so on those compilers the type of an astral first letter says it's unchanged while the runtime maps it.
- **A non-string returns the `fallback` option, `""` by default,** as [trimBlank](trim-blank.md) does, and a boxed string is unwrapped first.
- **A lone surrogate has no case,** so it's kept.

## Why

- **Matching `Capitalize<S>` keeps the type honest:** the package promises precise types ([What every export promises](package-promise.md) names `upperFirst("hello")` as its example), and every TypeScript version measured, 4.9 to 7.0, uppercases with full mapping rather than titlecasing.
- **Code points fix what most helpers get wrong.** es-toolkit, remeda, the native `charAt(0)` idiom, Hermes, .NET, Kotlin, Groovy, and Spring all leave `"𐐨a"` unchanged, because they look at one UTF-16 unit; lodash, Commons Lang, Java's code-point version, Python, Rust, and Go map it, and TypeScript itself now does.
- **Titlecase was rejected** because JavaScript has no titlecase mapping to build it on.
  - Commons Lang, Go's `unicode.ToTitle`, Kotlin's `titlecase()`, and Python's `capitalize()` titlecase (`"ǅa"`, and `"Ssa"` in Kotlin and Python), but a table of titlecase exceptions would be data the package ships and keeps current by hand.
  - The difference touches only the Latin digraphs (`ǆ`, `ǉ`, `ǌ`, `ǳ`), `ß`, the ligatures, and Georgian.
- **Leaving the rest alone by default** is what `upperFirst` means in lodash and es-toolkit, and keeps the function from destroying an acronym or an intentional `camelCase`.
  - `lowerRest` covers `capitalize` without a third export (owner, 2026-10-28).
- **Locale-free by default** gives the same answer everywhere; `locale` is opt-in, for callers who need Turkish, Azerbaijani, or Lithuanian casing and accept that it follows the engine.
  - Node, Java, and .NET agree on Turkish and Azerbaijani; Hermes ignores the tag, and only Node and Java apply Lithuanian's rule.
  - Falling back on a rejected tag, rather than returning the fallback, keeps the caller's text: Java and Hermes also ignore a bad tag, while Node and .NET throw.

## Consequences

- The README documents the length change (`"ß"` → `"SS"`) and the uppercase-not-titlecase choice, with `"ǆ"` as the example.
- The README notes that on TypeScript before 6.0 the type of an astral first letter lags the runtime.
- The README says `locale` follows the engine's locale data, with the Hermes result as the example, as AGENTS.md asks of an engine difference.
- The signature needs overloads: with no `locale`, the return is `Capitalize<S>` (or `Capitalize<Lowercase<S>>` with `lowerRest`); with `locale`, `string`.
- Case mapping follows each engine's Unicode version; the tests pin the characters above, not the whole table.
