# What safeParseBigInt accepts

`safeParseBigInt` reads an integer of any size into a `bigint`, by the same rules as `safeParseInt`, and returns the caller's fallback for anything else.

## Decision

- **Signature:**

  ```ts
  safeParseBigInt(value: unknown, options?: { clamp?: boolean; fallback?: F; max?: bigint | number; min?: bigint | number; radix?: number }): bigint | F
  ```

- **Accepted input:**
  - a bigint, returned as-is;
  - a number for which `Number.isSafeInteger` holds, converted exactly (`42` → `42n`, `-0` → `0n`);
  - a string that, after trimming, is an optional `+` / `-` and one or more ASCII digits (`"042"` → `42n`, `"-0"` → `0n`).
    - Trimming uses the internal `trimBlank`, so it strips the same blank characters as `safeParseNumber` (whitespace, zero-width and other invisible characters, and the braille blank) from both ends: `"\u200B42"` parses.
- **Everything else returns the fallback,** never a coercion:
  - blank and whitespace-only strings (`BigInt("")` and `BigInt("   ")` are `0n`);
  - a fraction or exponent (`"1.5"`, `"1.0"`, `"1e3"`), which no bigint parser measured accepts;
  - an `n` suffix (`"10n"`), which is literal syntax in code, not text a user types; `BigInt("10n")` throws too;
  - hex, binary, and octal strings without a `radix` (`"0x1A"`, `"0b11"`, `"0o17"`), which `BigInt()` accepts;
  - trailing text (`"12px"`), digit separators (`"1_000"`, `"1,000"`), digits from other scripts (`"٤٢"`), and `"Infinity"`;
  - a number that isn't a safe integer: `42.5`, `NaN`, `±Infinity`, and `1e21`, since a number past 2⁵³ has already lost its exact digits, and `BigInt(1e21)` would hand back the rounded double as though it were exact;
  - `null`, `undefined`, booleans (`BigInt(true)` is `1n`), arrays (`BigInt(["7"])` is `7n`), and objects.
- **A boxed primitive is unwrapped first,** by brand check, as every parser does: `new String(" 42 ")`, `new Number(1)`, and `Object(1n)` parse.
- **`radix` mirrors `safeParseInt`'s:** an integer from 2 to 36, defaulting to 10.
  - With a radix, a string is an optional `+` / `-`, then optionally the prefix that matches the radix (`0x` for 16, `0o` for 8, `0b` for 2, in either case), then digits valid in that radix, in either case.
  - So `"-0x1A"` with radix 16 is `-26n`, though `BigInt("-0x1A")` throws, and `"ff"` with radix 16 is `255n`, though `BigInt()` has no way to read it.
  - Without a `radix`, nothing is guessed: `"0x1A"` returns the fallback, unlike `BigInt("0x1A")`, which is `26n`.
  - Numbers and bigints are already values, so `radix` doesn't apply to them; a `radix` that isn't an integer from 2 to 36 returns the fallback for every input.
- **`min` and `max` are inclusive bounds,** as in `safeParseInt`, and each is a bigint or a safe-integer number (`min: 0` and `min: 0n` mean the same).
  - By default, a value outside them returns the fallback; `clamp: true` returns the nearest bound instead.
  - A number bound is converted to a bigint first, so every comparison is between two bigints.
  - A bound that is neither a bigint nor a safe-integer number (`0.5`, `NaN`, `Infinity`, `"10"`), or `min` greater than `max`, returns the fallback for every input rather than guessing which bound the caller meant.

## Why

- `BigInt()` throws on bad text (`SyntaxError`) and on a fraction (`RangeError`), yet turns `""`, `"   "`, `true`, and `[]` into `0n` or `1n`; a total parser has to reject both kinds of surprise.
- Every bigint parser measured outside JavaScript rejects `""`, `"1.0"`, and `"1e3"`: .NET's `BigInteger.Parse`, Java's `BigInteger`, Kotlin, Go's `SetString`, and Python's `int`.
- Fractions and exponents stay out even where the value is an integer, unlike `safeParseInt`, which accepts `"1.0"` and `"1e3"`:
  - no bigint parser measured accepts them;
  - an exponent lets a few bytes of text ask for an enormous number (`"1e1000000000"` is a billion digits), which a bigint, unlike a double, would actually build.
- The `radix` and the bounds mirror `safeParseInt`, so the two parsers differ only in the type they return and in what that type can hold.
  - The JavaScript prefixes come from the same rule: `BigInt()` reads `0x` / `0o` / `0b` itself but rejects a signed one (`"-0x1A"`), and Go's `SetString(value, 0)`, Commons Lang, and Spring read the signed form.
- Bounds take a safe-integer number as well as a bigint, since `min: 0` is the natural way to write a lower bound; converting it first keeps every comparison between two bigints, and a number past 2⁵³ is rejected for the same reason a value is.
- GitHub code search, on 2026-10-20, found `safeParseBigInt` in 168 files, `tryParseBigInt` in 1,032, `safeBigInt` in 3,328, and `parseBigInt` in 24,320 (approximate, every language; `toBigInt` collides with other libraries' APIs).
  - The `safeParse` name fits the parser rule in [When a name starts with `safe`](safe-prefix-naming.md).

## Consequences

- A caller with a number past 2⁵³ who wants its exact double value calls `BigInt(value)` directly; `safeParseBigInt` won't pretend the digits are exact.
- `safeParseBigInt` doesn't cap the length of its input: a million-digit string builds a million-digit bigint, so a caller reading untrusted text bounds its length first.
- Decimal amounts of any size belong to an exact-decimal library, which [What the package leaves to native APIs and other libraries](native-first-scope.md) already leaves to others.
