# What safeParseRegExp accepts

`safeParseRegExp` builds a `RegExp` from text the caller didn't write, such as a search box or a config file, and returns the caller's fallback where `new RegExp` would throw.

## Decision

- **Signature:**

  ```ts
  safeParseRegExp(value: unknown, options?: { fallback?: F; flags?: string; matchLiterally?: boolean }): RegExp | F
  ```

- **The name** follows [When a name starts with `safe`](safe-prefix-naming.md): it reads text into a `RegExp`, so it's a parser, as [`safeParseUrl`](safe-parse-url.md) is for the `URL` constructor.
- **Accepted input:**
  - a string, as the pattern;
  - a boxed string, unwrapped by brand check;
  - a `RegExp`, copied with its own flags unless `flags` is given, as `new RegExp(regexp, flags)` copies it, so the result never shares `lastIndex` with the caller's;
  - anything else returns the fallback, where the native constructor coerces it: `new RegExp(42)` is `/42/`, `new RegExp(null)` is `/null/`, and `new RegExp(undefined)` is `/(?:)/`.
- **Nothing is trimmed.** Whitespace is part of a pattern (`" "` matches a space), so the blank trimming the other parsers do would change what it matches.
  - `""` returns the fallback, since the empty pattern matches everywhere, which input that arrives empty almost never means; `" "` is a real pattern and parses.
- **Every pattern and flag the engine rejects returns the fallback,** wherever `new RegExp` throws `SyntaxError`:
  - unbalanced or dangling syntax: `"("`, `"["`, `"*"`, `"a**"`, a lone `"\\"`;
  - an out-of-order quantifier range: `"a{2,1}"`;
  - syntax other engines accept but JavaScript doesn't: an inline flag group with no colon (`"(?i)abc"`, which Python, Java, Go, and .NET read), and a group name repeated outside alternatives (`"(?<n>a)(?<n>b)"`);
  - an unknown, repeated, or wrongly cased flag (`"x"`, `"gg"`, `"G"`), and `u` with `v`.
- **`flags` is the native constructor's second argument, by name,** as [How a function takes its parameters](function-parameters.md) asks of a native call's optional configuration: `safeParseRegExp("a", { flags: "gi" })` is `/a/gi`.
- **`matchLiterally: true` escapes the text first, so it matches itself:** `safeParseRegExp("1.5 (a+b)?", { matchLiterally: true })` matches the string `"1.5 (a+b)?"` and nothing else.
  - The escaping produces exactly what `RegExp.escape` returns (`"\\x31\\.5\\x20\\(a\\+b\\)\\?"`), safe inside any pattern and with any flag, `v` included.
  - It's portable code: `RegExp.escape` exists in Node 24 and later but not in Node 22 (the `engines` floor) or Hermes 0.13, measured on 2026-10-21, and checking for it would be an environment probe.
  - A `RegExp` passed in is already a pattern, so `matchLiterally` doesn't apply to it; it's copied as it is.
- **Engine differences are documented, not smoothed over.** Which syntax parses is the engine's: Node 26 accepts pattern modifiers (`"(?i:abc)"`), a group name repeated across alternatives (`"(?<n>a)|(?<n>b)"`), and the `v` flag, while Hermes 0.13 rejects all three.
  - The function never rewrites a pattern to make it parse elsewhere, so the same input can be a `RegExp` on one runtime and the fallback on another, exactly as `new RegExp` succeeds on one and throws on the other.
- **A pattern that parses can still be slow to match.** Catastrophic backtracking (ReDoS, such as `"(a+)+$"` on a long run of `a`s) is a property of the pattern and the input, not of parsing it, so `safeParseRegExp` makes no promise about it; `matchLiterally` is the safe choice for text that should only ever match itself.

## Why

- `new RegExp(text)` throws on text a user can type, `"("` or `"*"` being enough, so every pattern built from input needs a `try`.
- Regex syntax differs by engine and by version, so the honest promise is "parses wherever this engine parses it":
  - Python and Java reject `"(?<n>a)|(?<n>b)"`, Python rejects `"(?<year>\\d{4})"` (it spells a named group `(?P<year>…)`) and `"\\p{L}"`, and Go's RE2 rejects lookbehind;
  - Hermes 0.13 lags the JavaScript spec itself, so a Node-only pattern can fail in React Native.
- An empty pattern is the one input whose result is valid but almost never meant: it matches every string, so a filter built from an empty search box would match everything instead of nothing.
- Escaping is the common case for user text, and the most-installed answer is a dependency:
  - GitHub code search, on 2026-10-21, found `escapeRegExp` in about 386,000 TypeScript and JavaScript files and `escapeRegex` in about 644,000, against about 44,000 calling `RegExp.escape(`;
  - npm's `escape-string-regexp` had about 217 million downloads in the week of 2026-10-12, and `lodash.escaperegexp` about 16 million;
  - so `matchLiterally` folds the escape into the parse, and matching `RegExp.escape`'s output keeps the result the same once the native method is everywhere.
- `matchLiterally` is a verb phrase, like the package's other boolean options (`clamp`, `ignoreCase`, `usePlusForSpace`), and says what the option does to matching rather than how: escaping is the mechanism, matching the text literally is the point.
- The search found `safeRegExp` in about 2,200 files and `toRegExp` in about 92,000; `safeParseRegExp` appears in none, but it's the name the parser rule gives, beside `safeParseUrl`.

## Consequences

- A caller who wants the empty pattern's match-everything behavior passes `{ fallback: /(?:)/ }`, or builds it with `new RegExp("")`.
- A pattern meant to run on Hermes as well as Node is tested on both; the function can't make a Node-only feature parse on Hermes.
- Escaping text for use inside a larger pattern, rather than as a whole pattern, needs `RegExp.escape` or a library; `safeParseRegExp` only escapes the whole text.
