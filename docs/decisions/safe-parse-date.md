# What safeParseDate accepts

`safeParseDate` reads a date the same way on every engine, and returns the caller's fallback for text no grammar can read without guessing; [`safeDateToIsoString`](date-to-iso.md) writes one back.

## Decision

- **Signature:**

  ```ts
  safeParseDate(value: unknown, options?: { fallback?: F; timeZone?: "local" | "utc" }): Date | F
  ```

- **Text is read by the package's own grammar, after trimming,** rather than by `Date.parse`, so every engine reads the same text the same way; trimming uses the internal `trimBlank`, as every parser does (`" 2024-01-01 "` and `"\u200B2024-01-01"` parse).
- **Three families of text parse:**
  - **the ECMAScript date-time string format:** `YYYY`, `YYYY-MM`, or `YYYY-MM-DD`, optionally followed by `THH:mm`, `:ss`, and a fraction, then an optional offset; expanded `±YYYYYY` years included (`"+010000-01-01T00:00:00Z"`), and `-000000` rejected, as the format rejects it;
  - **RFC 3339's extras:** a space for the `T` (`"2024-01-01 12:34:56Z"`), as PostgreSQL and SQLite print, and a lowercase `t` or `z`;
  - **the two formats `Date` writes itself:** `toUTCString`'s, which is also the HTTP date (`"Mon, 01 Jan 2024 00:00:00 GMT"`), and `toString`'s (`"Mon Jan 01 2024 12:00:00 GMT+0200 (Eastern European Standard Time)"`), whose closing time zone name, which each engine words differently, is skipped.
- **An offset is `Z`, `GMT`, or a sign with hours and optional minutes, colon or not:** `+02:00`, `+0200`, and `+02` all mean two hours east, so PostgreSQL's `timestamptz` text (`"2024-01-01 12:34:56+00"`) reads.
- **A fraction of any length is truncated to milliseconds** (`".789123"` → `.789`), so text from Python, Go, Java, and .NET, which write micro- and nanoseconds, reads.
- **Every date is checked against the calendar,** so nothing rolls over: `"2023-02-29"`, `"2024-13-01"`, `"2024-01-32"`, and the leap second `"T23:59:60"` return the fallback.
  - `T24:00`, with zero minutes, seconds, and fraction, is the midnight that ends the day, as the ECMAScript format allows: `"2024-01-01T24:00:00Z"` is `2024-01-02T00:00:00.000Z`; `"T24:00:01"` returns the fallback.
  - A weekday that contradicts the date (`"Tue, 01 Jan 2024 …"`, a Monday) returns the fallback, since the text disagrees with itself.
- **`timeZone` decides text with no offset; text with an offset ignores it.**
  - Unset, the ECMAScript rule applies, as `new Date(text)` reads it today: a date alone is UTC midnight, and a date and time is local time.
  - `timeZone: "utc"` reads every offset-less text as UTC, the same instant on every machine.
  - `timeZone: "local"` reads every offset-less text as local time, a date alone included, as date-fns and Day.js read it.
  - Local time is the runtime's own: the same code runs everywhere, through `Date`'s local-time arithmetic, but its answer moves with the machine's time zone setting, so `timeZone: "utc"` is the choice for results that never vary.
  - It also follows the runtime's time zone database (ICU's tzdata), so a historical date in a zone whose rules have changed can read differently on an older engine.
- **Everything else returns the fallback:** the basic format (`"20240101"`), free-form and locale text (`"Jan 1 2024"`, `"2024/01/01"`), digits (`"1704067200000"`), and blank text, however a given engine's `Date.parse` reads them.
- **A `Date` or a finite number is accepted as [`safeDateToIsoString`](date-to-iso.md) accepts it:** a valid `Date` from any realm is copied, a number in the `Date` range is epoch milliseconds, and a boxed string or number is unwrapped; an invalid `Date`, a number out of range, `NaN`, booleans, `null`, and objects return the fallback.
- **It returns a new `Date`,** never the caller's, so mutating the result can't reach the input.

## Why

- `Date.parse` is only predictable for the ECMAScript format, and the measured engines disagree even inside it:
  - Hermes 0.13 rolls invalid dates over (`"2024-13-01"` → 2025, `"2023-02-29"` → March 1, `"T23:59:60"` → the next day), and Node 26 rolls February 29 over too, while luxon and every language outside JavaScript reject them;
  - outside the format, V8 reads `"Jan 1 2024"`, `"2024/01/01"`, and a space-separated time as local time, which the `TZ="America/New_York"` column shifts by five hours, while Hermes rejects some of the same text;
  - so the grammar is the package's own, applied before any `Date` is built, and the result is assembled from its parts with `Date`'s own arithmetic, which every engine shares.
- ECMA-262 fixes the meaning of only one format, the Date Time String Format; it asks that `Date.parse` read back an engine's own `toString` and `toUTCString`, and leaves everything else to "implementation-specific heuristics".
  - The two formats `Date` writes are precise patterns, so reading them by grammar makes the round trip work on every engine, not just the one that wrote them; `toUTCString`'s is the HTTP date of `Date`, `Last-Modified`, `Expires`, and cookies.
  - RFC 3339's space and lowercase letters, and the hour-only and colon-less offsets, are what databases and other languages write; free-form and locale text stays out, since no grammar can read it without guessing.
  - The grammar is wide from the start because loosening a published check later is a breaking change.
- The default `timeZone` keeps `new Date(text)`'s answers for the text both accept, so moving to `safeParseDate` changes only what used to throw or roll over; `"utc"` and `"local"` are there for code that wants one rule for every offset-less text.
- Moment.js's strict ISO mode, `moment(value, moment.ISO_8601, true)`, is the nearest tool measured: it reads the same offset spellings, the space separator, and `T24:00`, and rejects every impossible date; it parts ways only on trimming, lowercase `t` and `z`, `Date`'s own formats, the basic format, and `-000000`.
- Accepting longer fractions matches what other languages write: Python's `isoformat`, Go's `RFC3339Nano`, and .NET's `"o"` emit six, nine, and seven digits, and Java and .NET read them back.
- `T24:00` is the one out-of-range time the ECMAScript format names as valid, and every JavaScript tool measured reads it as the next midnight; `-000000` is rejected because the format forbids it as a second spelling of year zero.
- `timeZone` is the option name `Intl.DateTimeFormat` uses; luxon calls the same idea `zone`.

## Consequences

- A caller with free-form or locale text, or a time zone name rather than an offset, reaches for a date library (luxon, date-fns, Temporal); `safeParseDate` reads the formats a grammar can read without guessing.
