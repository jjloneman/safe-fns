# How toMs converts a duration

`toMs({ minutes: 2.5 })` is `150000`: it replaces `Duration.fromObject(…).toMillis()` from luxon, and the hand-multiplied `2.5 * 60 * 1000`, with a dependency-free call that rejects a typo instead of returning `0`.

## Decision

- **Signature:**

  ```ts
  type ToMsDuration = {
    days?: number;
    hours?: number;
    milliseconds?: number;
    minutes?: number;
    seconds?: number;
    weeks?: number;
  };

  toMs<F = undefined>(
    duration: ToMsDuration,
    options?: { fallback?: F },
  ): number | F
  ```

  - `duration` is the one value the function works on, so it's positional, as [How a function takes its parameters](function-parameters.md) asks.
  - It takes typed input, as [the package promise](package-promise.md) allows, but checks it at runtime all the same, so a value from JSON or a cast is safe to pass.
  - The name stays `toMs`, the owner's, under [the naming rule](safe-prefix-naming.md)'s plain names.

- **Six units, with fixed lengths:** `weeks` (7 days), `days` (24 hours), `hours`, `minutes`, `seconds`, and `milliseconds`, named in the plural as `Temporal.Duration` and luxon name them.
  - A day is always 24 hours: the result is an amount of time, such as a timeout, not a step on a calendar, so a daylight-saving change never applies.
- **An unknown key returns the fallback,** so a typo is caught rather than read as `0`:
  - `months` and `years`, whose length varies; the compared libraries guess three different months, 30, 30.42, and 30.44 days;
  - singular names (`minute`) and abbreviations (`mins`, `ms`);
  - `microseconds` and `nanoseconds`, which a whole-millisecond result can't hold.
- **Every value must be a finite number:**
  - a fraction is fine, so `{ minutes: 2.5 }` and `{ minutes: 2, seconds: 30 }` are both `150000`;
  - a negative value is fine, and units with different signs add up, so `{ hours: 1, minutes: -15 }` is `2700000`;
  - `undefined` means the unit is absent, as an optional property does, so `{ minutes: undefined }` is `0`;
  - a string (`"5"`), `null`, a bigint, `NaN`, or `±Infinity` returns the fallback, never a coerced number.
- **`{}` is `0`:** no units is no time, as luxon, date-fns, Day.js, Moment.js, and Python's `timedelta` all agree.
- **The result is whole milliseconds, rounded half away from zero:**
  - `{ hours: 1.1 }` is `3960000`, not `3960000.0000000005`;
  - `{ milliseconds: 0.5 }` is `1` and `{ milliseconds: -0.5 }` is `-1`, so `toMs` of a negated duration is the negated result;
  - `-0` comes back as `0`.
- **A result past `Number.MAX_SAFE_INTEGER` either way returns the fallback,** since past it whole milliseconds can't all be told apart; `{ days: 100_000_000 }` (about 274,000 years) still fits.
- **Only a plain object is read,** as [isPlainObject](is-plain-object.md) defines one: a prototype of `Object.prototype` or `null`.
  - Its own enumerable string keys are read once each; inherited keys and symbol keys are ignored.
  - A `Temporal.Duration`, a class instance, an array, a number of milliseconds, or a string such as `"5m"` returns the fallback; a `Temporal.Duration` keeps its fields on its prototype, so reading it as an object would give a silent `0`.
- **Everything else returns the `fallback` option, `undefined` by default,** as [the parsers'](parser-fallbacks.md) does: anything that throws, such as a revoked proxy or a throwing getter, and an options object that can't be read.
- **It is arithmetic only,** so it runs the same in every runtime, Hermes included, with no `Temporal` or `Intl` needed.

- Each tool gets the same object; a tool's own calendar rules show, such as Temporal needing a reference date for `weeks`.

## Why

- **Not `Temporal.Duration`:** it's the native API, but `Temporal.Duration.from(…).total("millisecond")` throws `RangeError` on a fraction (`{ minutes: 2.5 }`), on `weeks` without a `relativeTo` date, and on mixed signs, and `TypeError` on `{}`; Hermes has no `Temporal` at all.
  - `toMs` is the arithmetic a caller writes when they want a plain number for `setTimeout` or a cache TTL, without a calendar.
- **Unknown keys fail:** luxon, Day.js, and Moment.js accept a singular `minute` as a synonym, but date-fns reads it as `0`, Moment.js reads `mins` as `0`, and Day.js reads it as `NaN`; a typo that silently becomes `0` makes a timeout fire at once.
  - Accepting only the plural names keeps one spelling per unit, the one `Temporal.Duration` uses.
- **No months or years:** date-fns makes a month 30.44 days, Day.js 30.42, and luxon and Moment.js 30; none of them is a calendar month, and a result that depends on which library is asked is no answer.
- **No coercion:** every JavaScript library compared reads `{ minutes: "5" }` as `300000` and `{ minutes: null }` as `0`, date-fns and Day.js read `NaN` as `0`, Moment.js returns `NaN`, and all three return `Infinity` for `Infinity`; Python's `timedelta` throws on all of them.
- **Whole milliseconds:** Day.js and luxon return `3960000.0000000005` for `{ hours: 1.1 }`, which leaks into logs and equality checks; date-fns truncates instead, so it reads `0.5` milliseconds as `0`, and drops a `milliseconds` key entirely (`698585000` where every other tool gives `698585004`).
  - Rounding half away from zero keeps the result symmetric around `0`; `Math.round` alone would make `-0.5` come out as `-0`.
- **A plain object only:** Moment.js and Day.js read a bare number as milliseconds (`5000` → `5000`) and a string by their own grammar, while date-fns and luxon reject both or read them as `0`; accepting only the documented shape, as [the narrow-check principle](../../AGENTS.md#-design-principles) asks, keeps one meaning per input.
- **The safe-integer limit:** every JavaScript tool returns `86400000000000000` for a billion days, a number whose last digits are no longer exact; Python's `timedelta` overflows past 999,999,999 days.

## Consequences

- The docs show `toMs({ minutes: 2.5 })` for `setTimeout`, and say that a day is 24 hours, that `months` and `years` aren't accepted, and that a typo returns the fallback.
- The docs point to `Temporal.Duration` for calendar-aware durations, and to [native-first-scope](native-first-scope.md)'s parked `formatDuration` for the reverse direction.
- Its tests cover each fallback case above, including a revoked proxy, a throwing getter, and a `Temporal.Duration` where one exists, and its type tests check that an unknown key and a string value are compile errors and that `fallback` widens the return type.
- **Migrating from luxon:** a `toMs` written as `Duration.fromObject(duration).toMillis()` is replaced call for call wherever it passes the six plural units, such as `{ minutes: 15 }` or `{ minutes: 1, seconds: 30 }`; the docs' migration note lists where luxon's `DurationLikeObject` answers differently:
  - singular keys (`{ minute: 5 }`) and `quarters`, `months`, and `years`, which luxon accepts with casual lengths (a 30-day month, a 365-day year), return the fallback;
  - a key luxon doesn't know throws `InvalidUnitError` there, and returns the fallback here;
  - a numeric string (`{ minutes: "5" }`) is coerced there, and returns the fallback here;
  - a fraction that doesn't land on a whole millisecond (`{ hours: 1.1 }`) is `3960000.0000000005` there, and `3960000` here;
  - the return type is `number | undefined`, not `number`: `setTimeout(fn, toMs(…))` still compiles, and arithmetic such as `Date.now() + toMs(…)` takes `{ fallback: 0 }` or `?? 0`.
- A benchmark compares it with luxon's `Duration.fromObject(…).toMillis()` and hand-written multiplication, per [the performance decision](performance.md).
