# What safeParseString accepts and returns

`safeParseString(value, { fallback })` turns a value that has an obvious text form into trimmed, non-blank text.

## Decision

- **Accepted input, and what it becomes:**
  - a string, trimmed of the same characters `isSafeEmpty` treats as blank (whitespace, zero-width and other invisible characters, and the braille blank), through the shared internal `trimBlank`;
  - a finite number, as `String(value)` (`1.5` → `"1.5"`, `1e21` → `"1e+21"`, `1e-7` → `"1e-7"`), except that `-0` keeps its sign as `"-0"`;
  - a bigint, as `String(value)` (`12n` → `"12"`);
  - a boolean, as `"true"` or `"false"`.
- **A boxed primitive is unwrapped first,** then parsed like the primitive it holds: `new String(" 42 ")`, `new Number(1)`, `new Boolean(false)`, and `Object(1n)`.
  - Each box is identified by a brand check (calling `String.prototype.valueOf` and its siblings, which read the hidden slot only a real box has and throw on anything else, cross-realm included), never by its shape.
  - Every parser in the package does the same, so a boxed value never behaves differently from one parser to the next.
- **`trim: false` keeps a string's surrounding whitespace.**
  - Blank input still returns the fallback, judged the same way, so only non-blank strings come back, unchanged.
  - It's the `defaultIfBlank` to the default's `trimToNull`, in Apache Commons Lang's terms.
- **A blank result returns the fallback,** judged by the same test as `isSafeEmpty` (see [What "empty" means](is-safe-empty.md)), so `""`, `"   "`, and `"\u200B"` never come back.
- **Everything else returns the fallback:**
  - `null`, `undefined`, `NaN`, and `±Infinity`;
  - symbols, functions, arrays, and objects, and anything with a custom `toString`.

## Why

- It replaces the `isNonBlankString` type guard, which [How predicates are named](predicate-naming.md) dropped: callers that wanted "a usable string or nothing" get it in one call.
- `-0` keeps its sign because the package fails safe toward preserving data, and a round trip through `safeParseNumber` would otherwise lose it; most languages measured keep it too (`"-0"` in lodash, es-toolkit, .NET, Go, Rust, and PHP; `"-0.0"` on the JVM, in Python, and in Ruby), while JavaScript's `String()`, JSON, and template literals write `"0"`.
- Boxed values are unwrapped because six of the seven JavaScript tools measured do (`String()`, lodash, es-toolkit, zod, valibot); only Ajv rejects them.
- The owner chose to stringify primitives, so a numeric ID or a boolean flag read from loosely typed data comes through as text.
- Objects are excluded because their text form is either `"[object Object]"` or a `toString` that can throw or lie.

## Consequences

- A caller that wants `-0` written as `"0"` normalizes the number first (`Math.abs(value)`, or `value === 0 ? 0 : value`).
- Numbers use JavaScript's own format, which `safeParseNumber` reads back; other languages each write `1e21` differently, so there's no shared format to follow.
- By default the returned string can differ from the input by its surrounding whitespace; a caller that needs the exact text passes `{ trim: false }`.
